# عقد بيانات ISLAM DETECTOR V2
الإصدار: مسودة هندسية 0.1  
الحالة: مقترح قيد المراجعة — ليس بروتوكول Firmware معتمداً بعد  
المسار: `docs/engineering/ISLAM_DETECTOR_V2_DATA_CONTRACT_AR.md`

## 1. الغرض والحدود

يحدد هذا المستند عقداً موحداً للبيانات بين STM32G474RE وESP32-S3 وتطبيق Android ومختبر ISLAM LAB. الغرض هو حفظ القياس الخام ومصدره وتوقيته وسلامته وربط كل تحليل بإصداره، دون خلط المحاكاة بالقياس الحقيقي.

هذا العقد لا يحدد توقيت النبضة النهائي أو عدد العينات أو دقة ADC أو قيم الملف أو إعدادات الطاقة. هذه أمور لا تزال تحتاج قراراً هندسياً وقياساً على العتاد. كما أنه لا يثبت أداء كشف أو عمقاً معيناً.

## 2. المسؤوليات

- **STM32G474RE:** المالك الوحيد لتوقيت الإثارة/الاستقبال وأخذ العينات المرتبطة بها. ينشئ معرف الالتقاط ورقم التسلسل والطوابع الزمنية المحلية، ويصدر العينات الخام مع معلومات حالة الالتقاط.
- **ESP32-S3:** ناقل اتصال ومنسق حزم بين اللوحة والهاتف. لا يعيد تفسير العينات ولا يغيرها ولا ينسب إليها نتائج كشف من عنده.
- **Android:** يستقبل الحزم، يتحقق من بنيتها وتسلسلها وسلامتها، ويحفظ الخام قبل التحليل أو العرض. يمكنه تنفيذ العرض والتحليل غير الحرج زمنياً.
- **ISLAM LAB:** يستورد نسخاً من التجارب، ويدير المراجعة والتقييم وإصدارات الخوارزميات. لا يرسل أوامر إلى مسار الالتقاط أثناء عمله، ولا يكتب فوق الخام.

## 3. فصل أنواع البيانات

يجب أن يحتوي كل سجل على حقل مصدر واضح، بقيمة واحدة من:

- `synthetic`: بيانات أنشأتها محاكاة أو مولد صناعي.
- `user_provided`: إدخال يدوي أو ملف خارجي غير موثق كقياس جهاز.
- `instrument`: جهاز قياس مختبري خارجي.
- `islam_detector`: التقاط من جهاز إسلام الفعلي.

ولا يجوز تحويل المصدر من نوع إلى آخر لمجرد مراجعة السجل أو تأكيد المستخدم له. كما يجب الفصل بين دورة حياة المراجعة وبين الحقيقة الأرضية: `review.lifecycle_status` يصف أين وصل السجل في سير العمل، أما `ground_truth.status` فيصف ما ثبت عن الهدف بدليل مستقل. لا يؤدي ضغط المستخدم على «هدف مؤكد» وحده إلى GROUND_TRUTH_CONFIRMED أو CONFIRMED؛ بل ينشئ حدث مراجعة يحتاج تحققاً موثقاً.

## 4. نموذج سجل الالتقاط

الحقول التالية هي الحد الأدنى المقترح لبيانات وصف الالتقاط:

| الحقل | النوع | المعنى |
|---|---|---|
| schema_version | نص | إصدار العقد، ويبدأ المقترح بـ `2.0.0` |
| capture_id | UUID | معرف فريد لا يعاد استخدامه |
| sequence | عدد صحيح غير سالب | رقم متزايد ضمن جلسة الجهاز |
| session_id | UUID | معرف جلسة القياس |
| captured_at_utc | نص ISO-8601 أو null | وقت مدني إن كان متاحاً؛ لا يستبدل الساعة الرتيبة |
| monotonic_start_tick | عدد صحيح | بداية الالتقاط على ساعة STM32 الرتيبة |
| tick_frequency_hz | عدد صحيح | تردد مرجع الساعة المستخدم لتفسير ticks |
| source.type | enum | أحد أنواع المصدر المحددة أعلاه |
| source.device_id | نص أو null | معرف الجهاز عند القياس من الجهاز |
| source.stm32_firmware | نص أو null | إصدار Firmware الخاص بـ STM32 |
| source.esp32_firmware | نص أو null | إصدار Firmware الخاص بـ ESP32 |
| coil_profile_id | نص | معرف إعداد الملف/المجس المستخدم؛ لا يفترض أنه DD32 |
| acquisition_config_id | نص | معرف إعداد الالتقاط وإصدار تعريفه |
| sample_encoding | enum | ترميز العينات الخام |
| sample_count | عدد صحيح موجب | عدد العينات الفعلي |
| sample_payload_sha256 | نص hex بطول 64 | بصمة الحمولة الخام |
| payload_length_bytes | عدد صحيح موجب | حجم الحمولة بالبايت |
| payload_crc32 | نص hex | كشف تلف النقل العرضي |
| transport_status | enum | complete أو incomplete أو corrupted |
| review.lifecycle_status | enum | CAPTURED أو NEEDS_REVIEW أو REVIEWED أو GROUND_TRUTH_CONFIRMED أو REJECTED أو INCONCLUSIVE أو ELIGIBLE_FOR_TRAINING |
| ground_truth.status | enum | UNKNOWN أو CONFIRMED أو REJECTED أو INCONCLUSIVE؛ لا يحدد إلا وفق دليل مراجعة موثق |
| reviewer_id | نص أو null | معرف المراجع عند وجود مراجعة |
| review_event_id | UUID أو null | مرجع حدث المراجعة؛ لا تحفظ التعديلات فوق السجل الخام |

كل حقل غير متاح يبقى null أو يوسم بأنه غير معروف وفق المخطط؛ لا نخترع قيماً افتراضية توحي بقياس لم يحدث.

## 5. الحمولة الخام Raw Payload

- تحفظ عينات ADC كأعداد صحيحة خام، لا كقيم mV محولة إلا إذا أرفقت أيضاً المعايرة التي تسمح بإعادة اشتقاق التحويل.
- تحفظ أزمنة العينات أو offsets بالنسبة إلى ساعة الالتقاط، بوحدة معلنة ومحددة.
- لا تفترض هذه المسودة أن ADC يعمل على قناة واحدة أو أن كل نافذة لها عدد عينات ثابت؛ تعريف القنوات والنوافذ سيأتي في ملف acquisition profile مستقل.
- يحفظ ترتيب القنوات والنوافذ صراحة ضمن وصف الحمولة، ولا يعتمد على ترتيب ضمني في التطبيق.
- تحفظ الحمولة الأصلية كما وصلت، ويمنع تعديلها بعد الحفظ. أي تصحيح أو تحويل ينتج artifact جديداً مع بصمة ورابط إلى الالتقاط الأصلي.
- CRC32 مخصص لكشف أخطاء النقل العرضية، وSHA-256 للتحقق من هوية المحتوى. لا يحل أحدهما محل الآخر.

## 6. فصل الالتقاط عن التحليل والتأكيد

سجل الالتقاط غير قابل للتعديل بعد اكتماله. تسجل العمليات اللاحقة كأحداث مستقلة:

1. `analysis_run`: معرف تشغيل، capture_id، algorithm_id، algorithm_version، model_sha256، إعدادات التشغيل، والنتائج المشتقة.
2. `review_event`: حالة المراجعة الجديدة، الحالة السابقة، سبب التغيير، المراجع، الوقت، ومصدر الدليل.
3. `evaluation_run`: مجموعة البيانات وبصمتها، فصل التدريب/التحقق/الاختبار، المقاييس، وقرار قبول المرشح أو رفضه.
4. `deployment_event`: إصدار الخوارزمية المعتمد، وقت التفعيل، الإصدار السابق، ونتيجة الرجوع إن حدث.

لا تعتبر نتيجة التحليل أو نسبة الثقة أو تسمية المستخدم جزءاً من القياس الخام.

## 7. بروتوكول النقل المقترح

الاقتراح المبدئي هو:
- رسائل التحكم والحالة والبيانات الوصفية بصيغة JSON محدودة الحجم.
- الحمولة الكبيرة للعينات الخام بإطار ثنائي ذي طول معلن وإصدار وترقيم.
- كل إطار يحمل message_type وprotocol_version وsession_id وsequence وpayload_length وchecksum.
- يدعم الاستقبال اكتشاف الفقد والتكرار وإعادة الإرسال أو طلب استكمال الحزمة بحسب ما يسمح به النقل.
- لا يقر التطبيق الالتقاط مكتملاً قبل تحقق الطول والبصمة/السلامة واكتمال تسلسل الأجزاء.
- لا يرسل ESP32 بيانات جزئية على أنها قياس كامل.

لم يُحسم بعد اختيار TCP أو WebSocket أو BLE أو غيره؛ لا يجوز ربط تعريف القياس بوسيلة النقل.

## 8. التوافق مع بيانات المختبر الحالية

- تبقى سجلات CSV ذات schema_version 1.1 و1.0.0 قابلة للقراءة كما هي.
- لا يعاد تصنيف السجلات القديمة إلى `islam_detector` دون دليل مصدر موثق.
- لا تتحول السجلات القديمة إلى 2.0.0 بمجرد تغيير قيمة الإصدار؛ يلزم تحويل صريح يسجل مصدر التحويل ويحتفظ بالنسخة الأصلية وبصمتها.
- يجب معالجة التعارض الحالي بين منتج CSV في `ExperimentData.toCsv()` (1.1) والتحقق الصارم في `ExperimentCsvValidator` (1.0.0) عبر اختبارات توافق؛ لا نكسر تصدير المختبر القديم في هذه المرحلة.
- يوصى بأن يخزن التطبيق الجديد payload الخام في BLOB أو ملف ثنائي محمي، والبيانات الوصفية في SQLite. CSV يبقى صيغة تبادل/تقرير لا الحاوية الأساسية الوحيدة للخام.

## 9. متطلبات سلامة التخزين

- يمنع `CONFLICT_REPLACE` في جدول الالتقاطات.
- يمنع الحذف المباشر للسجل الخام من واجهة التشغيل العادية.
- التصحيحات والمراجعات أحداث append-only؛ لا تستبدل الحالة السابقة دون الاحتفاظ بها.
- أي حذف إداري استثنائي يجب أن يسجل في audit log مع السبب والفاعل والوقت، وفق سياسة احتفاظ منفصلة.
- تحفظ بصمة الخام وبصمة كل artifact مشتق، مع روابط المصدر.
- تكون كتابة الالتقاط مع البيانات الوصفية معاملة ذرية؛ إما أن يحفظ السجل كاملاً أو لا يظهر كسجل مكتمل.

## 10. اختبارات القبول المطلوبة قبل اعتماد العقد

1. قبول سجل instrument صحيح ورفض سجل ينقصه مصدر أو وحدة أو تعريف توقيت.
2. رفض أي سجل synthetic يدعي ground_truth_confirmed.
3. كشف payload ناقص أو CRC خاطئ أو SHA-256 غير مطابق.
4. كشف sequence مكرر أو مفقود أو خارج الترتيب دون دمج العينات بصمت.
5. إثبات أن حفظ الالتقاط ثم إغلاق قاعدة البيانات وإعادة فتحها لا يغير البايتات أو البصمة.
6. إثبات أن تعديل label ينشئ review_event جديداً ولا يغير الخام أو الأحداث السابقة.
7. إثبات أن فشل التحليل أو امتلاء مساحة التخزين لا يوقف توقيت STM32 أو يفسد التقاطاً جارياً.
8. اختبار توافق استيراد CSV 1.1 و1.0.0 دون تغيير مصدر البيانات أو حالة التحقق.
9. اختبار تحويل قديم إلى 2.0.0 مع الاحتفاظ بالملف الأصلي وبصمته ومعلومات التحويل.
10. اختبار الضغط وفقد الاتصال وإعادة الاتصال على عتاد فعلي قبل تثبيت حدود أحجام الحزم ومعدلات النقل.

## 11. ما لم يُحسم

- قناة/قنوات ADC وترتيبها ومجالها الفعلي.
- معدل أخذ العينات ودقة التوقيت ومصدر الساعة.
- بنية نوافذ القياس وطريقة ترقيمها.
- ملف الإثارة والاستقبال ومعرفات إعداداتها.
- الحد الأعلى لحجم الالتقاط ومعدل النقل.
- وسيلة النقل النهائية بين اللوحات والهاتف.
- صيغة التخزين الثنائية النهائية وإصدارها.

**حالة الاعتماد:** هذه المسودة تصلح أساساً للمراجعة والاختبارات البرمجية، ولا يجوز اعتبارها مواصفة عتاد نهائية أو البدء بتصنيع PCB اعتماداً عليها وحدها.
