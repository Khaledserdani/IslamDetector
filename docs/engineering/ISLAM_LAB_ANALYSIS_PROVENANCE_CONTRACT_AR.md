# عقد مصدر نتائج الكشف وسلسلة منشئها — ISLAM LAB

## الحالة الحالية

هذا العقد يحدد متطلبات الربط المستقبلي، ولا يدّعي أن محرك كشف ميدانياً موجود أو أن الربط قد نُفذ.

الفحص على فرع `feature/islam-lab-foundation` وجد:

- `PiPulseEngine.simulate(PiPulseInput)` محرك محاكاة دائرة PI مختزلة، مع حلقة هدف مكافئة واحدة وخرج RX مفتوح الدائرة.
- `SyntheticDecayModel.simulate(...)` مولّد موجة اختبار اصطناعية حتمية.
- `PiPulseAnalysisActivity.executePulse(...)` يستدعي محرك المحاكاة على خيط منفصل ويعرض التقرير؛ لا يتصل بجهاز STM32 أو ESP32 ولا يلتقط عينات ADC.
- `ScientificCaptureStore.appendAnalysisRun(AnalysisInput)` يقبل `resultJson` من المستدعي. لذلك فهو مخزن سجل، وليس جهة إثبات أن النتيجة خرجت من محرك موثوق.
- جدول `analysis_runs` الحالي يسجل capture digest والخوارزمية والإصدار وبصمة النموذج والإعدادات والنتيجة والأوقات والحالة، لكنه لا يسجل بصمة كود التنفيذ أو بصمة بناء المحرك أو بصمة إعدادات منفصلة أو هوية runtime.

يجب أن تبقى نتائج المحاكاة والبيانات الاصطناعية في مساراتها الموسومة، ولا يجوز أن تتحول إلى `instrument` أو `islam_detector` أو أن تدخل تقييم FIELD_CANDIDATE.

## المبدأ المعماري

الجهة التي تملك التنفيذ هي وحدها التي تنشئ نتيجة التحليل. لا تقبل واجهة Android أو شاشة المختبر أو مستورد CSV نتيجة مكتملة يدوياً.

التدفق المقصود:

1. يستقبل مسار الاستحواذ حزمة خام مكتملة من الجهاز.
2. يتحقق من هوية الجهاز، رقم التسلسل، تنسيق الحمولة، عدد العينات، حالة النقل، وبيانات firmware/configuration.
3. يحفظ الحمولة مرة واحدة في `captures` ويستخرج `capture_id` وSHA-256 من المخزن نفسه.
4. يقرأ محرك الكشف سجل الالتقاط المحفوظ؛ لا يستقبل digest مستقلاً يمكن أن لا يطابق البايتات.
5. ينفذ الخوارزمية المحددة على الحمولة نفسها، مع snapshot ثابت للإعدادات والنموذج.
6. ينشئ المحرك كائن نتيجة داخلياً غير قابل للتعديل، ويحسب بصمات المخرجات والإعدادات والبناء.
7. يستدعي adapter داخلياً في طبقة الثقة لتسجيل التشغيل؛ لا يكون adapter متاحاً كواجهة عامة لشاشة UI أو استيراد CSV.
8. يعيد سجل التشغيل معرفه ونتيجته للعرض. فشل التسجيل لا يغيّر بيانات الالتقاط الخام ولا يوقف الاستحواذ؛ يسجل كخطأ منفصل ويعاد التعامل معه وفق سياسة موثقة.

لا يجوز أن يتوقف التقاط الجهاز أو حلقة التوقيت في STM32 بسبب الكتابة إلى قاعدة بيانات Android أو تأخر الشبكة. يجب أن يكون التخزين والتحليل خارج مسار التوقيت الحرج، مع queue محدودة وسلوك overflow واضح لا يسقط القياسات بصمت.

## الحقول المطلوبة في سجل التحليل

| الحقل | الغرض |
|---|---|
| analysis_run_id | معرف فريد لكل تنفيذ، لا يعاد استخدامه |
| capture_id + input_payload_sha256 | ربط التنفيذ بالحمولة الخام الدقيقة |
| algorithm_id + algorithm_version | تعريف الخوارزمية المنفذة |
| source_commit_sha | commit مصدر الكود الذي بني منه المحرك |
| engine_artifact_sha256 | بصمة ملف البناء التنفيذي الفعلي |
| model_sha256 | بصمة أوزان النموذج أو NULL إذا لم يوجد نموذج |
| parameters_json + parameters_sha256 | snapshot حتمي للإعدادات وبصمتها |
| result_json + result_sha256 | خرج المحرك بعد canonical serialization وبصمته |
| engine_id + runtime_version | تعريف محرك التنفيذ وبيئة التشغيل |
| device_id + firmware identities | الجهاز والبرمجيات الثابتة ذات الصلة |
| started/completed timestamps | زمن التنفيذ، مع monotonic clock عند توفره |
| run_status + failure_code | complete/failed/cancelled وسبب فشل منضبط |

يجب أن تتطابق بصمة `input_payload_sha256` مع بصمة سجل الالتقاط المحفوظ. ويجب رفض التشغيل المكتمل إذا غابت بصمة البناء أو بصمة الإعدادات أو النتيجة أو كان أي منها غير صالح. لا تُستخدم قيمة placeholder أو hash ثابت مشترك.

## حدود الثقة

- SHA-256 يثبت تطابق البايتات، لكنه لا يثبت وحده أن البرنامج الذي أنتجها موثوق.
- حفظ `source_commit_sha` و`engine_artifact_sha256` يوفر provenance قابلاً للتدقيق، لكنه لا يمنع مالك قاعدة البيانات أو تطبيقاً معدلاً من تزوير السجلات.
- توثيق مصدر حقيقي أقوى يتطلب لاحقاً توقيع بناء/attestation موثوقاً، والتحقق من توقيع التطبيق أو firmware، وإدارة مفاتيح لا تحفظ أسرارها داخل قاعدة البيانات القابلة للتعديل.
- `reviewer_id` و`approved_by` النصيان الحاليان لا يمثلان مصادقة هوية.
- لا تعتمد أي ترقية Candidate على بيانات محاكاة أو بيانات يدوية أو سجل تحليل لا يثبت منشأه.

## حالات الاختبار المطلوبة قبل ربط المحرك

1. رفض نتيجة مكتملة إذا اختلف digest عن الحمولة.
2. رفض نتيجة مكتملة إذا غابت بصمة build أو parameters أو result.
3. رفض بصمة بناء غير SHA-256 أو إعدادات غير canonical.
4. إثبات أن تغيير بايت واحد في الحمولة ينتج capture digest مختلفاً ويرفض ربط التشغيل القديم.
5. إثبات أن فشل التحليل يسجل failed ولا يغير capture.
6. إثبات أن تشغيل UI أو CSV لا يستطيع إنشاء تحليل مكتمل موثوق.
7. إثبات أن المصدر synthetic/user_provided لا يمر إلى FIELD_CANDIDATE.
8. اختبار queue overflow وانقطاع Wi-Fi بحيث لا تتوقف حلقة الاستحواذ أو تضيع البيانات بصمت.
9. اختبار إعادة تشغيل التطبيق أثناء وجود عناصر انتظار، ومنع تكرار أو ضياع سجل التحليل.
10. اختبار ربط نتائج Champion وCandidate بالحمولة نفسها وبإصدارات وبصمات بناء محددة.

## قرار التنفيذ

لا نضيف adapter وهمياً ولا نسجل خرج `PiPulseEngine` أو `SyntheticDecayModel` على أنه كشف ميداني. الخطوة البرمجية التالية بعد وجود مسار استحواذ حقيقي هي إضافة provenance schema/ migration وواجهات داخلية typed، ثم ربط المحرك الفعلي واختبارات التكامل. إلى ذلك الحين تبقى بوابة FIELD_CANDIDATE غير قابلة للاستخدام كإثبات أداء جهاز حقيقي.
