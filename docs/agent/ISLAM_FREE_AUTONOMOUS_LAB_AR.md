# ISLAM FREE AUTONOMOUS LAB — الأساس المعماري

تاريخ القرار: 2026-11-18

## الهدف
بناء وكيل مساعد مفتوح المصدر ومخصص لمشروع ISLAM DETECTOR، دون اشتراكات أو مفاتيح API مدفوعة أو خدمات استضافة مدفوعة. المطلوب أن ينجز أعمال مراجعة وتحليل واختبار متكررة، ويحفظ ذاكرة المشروع، ويصدر تقارير قابلة للمراجعة.

## الحقيقة التقنية: مستويان مختلفان

### المستوى A — سحابي مجاني ومجدول
- يستخدم GitHub Actions القياسي في هذا المستودع العام لتشغيل فحوصات دورية ومهام محددة.
- كل تشغيل يبدأ في بيئة مؤقتة جديدة؛ لا يوجد خادم دائم ولا ذاكرة RAM مستمرة.
- تحفظ الذاكرة في ملفات versioned داخل المستودع، وتحفظ تقارير التشغيل كسجلات أو Artifacts عند الحاجة.
- يمكنه تشغيل اختبارات Python، تدقيق ملفات التصميم، التحقق من اتساق الوثائق، وإنتاج تقارير.
- لا يفترض وجود نموذج لغوي أو API خارجي. في غياب نموذج لغوي، تكون القرارات الآلية محددة بقواعد واختبارات، لا ادعاء ذكاء توليدي.

### المستوى B — عقل لغوي محلي مجاني (اختياري)
- عند توفر حاسوب يملكه المستخدم ويبقى قيد التشغيل، يمكن تشغيل Ollama ونموذج مفتوح مناسب محلياً.
- يتصل المنسق المحلي بمستودع GitHub عبر صلاحيات محدودة، ويستخدم النموذج المحلي للتخطيط وشرح النتائج واقتراح التعديلات.
- لا توجد رسوم API، لكن الجهاز يستهلك الكهرباء والإنترنت والموارد المحلية.
- دون جهاز محلي أو خادم مجاني دائم موثوق، لا يمكن ضمان وكيل لغوي يعمل 24/7 بلا انقطاع.

## المعمارية المقترحة
1. Scheduler: تشغيل مجدول ومشغلات يدوية وعند Pull Request.
2. Project Memory: ملف ذاكرة وسجل قرارات مؤرخ.
3. Task Queue: مهام صغيرة محددة الأولوية والقبول.
4. Tools: اختبارات Python، فحوصات ساكنة، سكربتات محاكاة، وGitHub API عبر GITHUB_TOKEN.
5. Evidence Ledger: لكل نتيجة الأمر المنفذ، commit، وقت التشغيل، الحالة، والقيود.
6. Report: تقرير عربي موجز يميز بين فحص ساكن، اختبار منفذ، محاكاة، وقياس حقيقي.

## حواجز السلامة والهندسة
- ممنوع تعديل main مباشرة أو دمج Pull Request تلقائياً.
- كل تغيير في فرع مستقل، ويُفتح كـ Draft PR للمراجعة.
- لا يغير ملفات التصميم الكهربائي أو قيم المكونات لمجرد أن اختباراً اصطناعياً نجح.
- لا يعتبر نتائج synthetic fixtures قياسات ميدانية.
- لا يعتمد قيمة محاثة أو عمق كشف دون مصدر أو تحقق مناسب.
- لا يرفع أسراراً أو Tokens إلى السجلات أو ملفات المستودع.
- صلاحيات GitHub الدنيا الممكنة؛ لا صلاحية نشر أو إدارة أسرار ما لم تثبت الحاجة.
- إذا فشل الاختبار أو تعذر تشغيله، يسجل ذلك بوضوح ولا يصدر تقرير نجاح.

## مراحل التنفيذ

### المرحلة 0 — الأساس
تثبيت القرار المعماري وحدود المجانية والاستقلالية.

### المرحلة 1 — نواة حتمية آمنة
إنشاء مشغل Python صغير يقرأ قائمة مهام مسموحة، يشغّل فحوصات محددة، يلتقط exit codes، ويكتب تقرير Markdown وJSON. لا يعدل ملفات المشروع.

### المرحلة 2 — تشغيل GitHub Actions
إضافة Workflow يدوي وعند Pull Request أولاً. بعد مراجعة المستخدم ودمجه في الفرع الافتراضي، يمكن تفعيل تشغيل دوري؛ لأن GitHub يشغّل أحداث schedule على أحدث commit في الفرع الافتراضي.

### المرحلة 3 — الذاكرة والطابور
إضافة سجل القرارات والمهام المنجزة والمؤجلة مع منع تكرار العمل.

### المرحلة 4 — العقل المحلي
إضافة تكامل اختياري مع Ollama عند توفر حاسوب مناسب. لا يكون شرطاً لتشغيل الفحوصات الحتمية.

### المرحلة 5 — صلاحيات التعديل المحدود
السماح بإنشاء فرع وفتح Draft PR فقط، بعد نجاح الفحوصات. لا دمج تلقائي.

## معنى «مستمر» في هذا التصميم
- نافذة التشغيل المحلية الافتراضية: 20:00 إلى 06:00 بتوقيت الجزائر، ويمكن تغييرها بخياري `--work-start` و`--work-end`.
- يدعم المجدول عبور منتصف الليل، ويبدأ/يوقف العامل عند حدود النافذة.
- أثناء النافذة، يمكن تشغيل تجارب DC/RLC/AC الحسابية المعتمدة تلقائياً بعد التحقق من المدخلات، وحفظ سجل نتائج قابل لإعادة المراجعة.
- أي اقتراح يتضمن كتابة مصدر أو تغيير مشروع أو إجراء غير مختبري يبقى معلقاً للموافقة البشرية؛ لا يوجد تعديل تلقائي غير مراقب للمصدر.

## معنى «مستمر» في هذا التصميم
- مجدول: يعمل في أوقات دورية عندما تسمح المنصة، وليس خادماً دائماً.
- دائم الذاكرة: تحفظ حالته في المستودع بين مرات التشغيل.
- مستقل ضمن حدود: ينفذ قائمة أعمال مصرحاً بها دون انتظار رسالة جديدة.
- ليس مضموناً 24/7: لا توجد استمرارية تشغيل لحظية أو ضمان توقيت من GitHub Actions.

## شرط الحفاظ على المجانية
المستودع الحالي عام، واستخدام GitHub-hosted standard runners للمستودعات العامة موضح من GitHub على أنه مجاني. يجب إعادة التحقق من سياسات GitHub عند التوسع، وتجنب larger runners وأي خدمة خارجية مدفوعة. لا نضيف بطاقة دفع أو خدمة مدفوعة.

## أول مهمة تنفيذية
بناء المرحلة 1 فقط: نواة تدقيق لا تكتب في ملفات المشروع، تبدأ بفحوصات آمنة لمجلد simulation/spiral، وتنتج تقريراً يذكر بوضوح ما تم تشغيله وما لم يتم تشغيله. بعد اختبارها، نضيف Workflow يدوي وPR في المرحلة 2.
